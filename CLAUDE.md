# CLAUDE.md

Guía para Claude Code cuando trabaja **dentro de este repo** (el repo de agentes, no el del producto).

## Qué es este repo

`agent-team-template` es un **marketplace de plugins de Claude Code** + el runtime de un equipo de agentes que opera un producto de software. No es un proyecto de software típico: no hay código compilado ni build. El "código" son manifests de plugins, archivos `SKILL.md`, configs de MCP, system prompts, wrappers de PowerShell, workflows de n8n y bases de conocimiento en markdown. En la raíz hay un `package.json` mínimo, **sin dependencias**, que solo junta scripts de npm (`env:*` para los secretos y `lead:*` para el Project Lead).

Lo consumen dos entornos:
- **Server headless** (Windows): n8n dispara `claude -p ...` por cron o por webhook.
- **Claude Code / Cowork desktop**: uso interactivo del owner para revisar y aprobar (HITL). Ahí corre también el **Project Lead** (ver más abajo).

`.claude-plugin/marketplace.json` declara cuatro plugins en `plugins/`:
- `team-shared` — brand voice, glossary, personas, design system y skills de contenido. El resto de los plugins depende de estas skills.
- `team-growth` — ads, SEO, AEO, monitoreo de funnel, email lifecycle, conversión, y los `.mcp.json`.
- `team-data` — queries de solo lectura (cohortes, ARPU, anomalías).
- `team-pm` — pipeline insight → propuesta → roadmap.

El **repo del producto** vive aparte (`project.json → productRepoPath`, por ejemplo `..\..\acme-app`). Es la fuente de verdad de stack, copy y modelo de datos: léelo antes de preguntarle al owner. Si el producto vive en varios repos, `project.json → productRepos` los declara todos (ver "Modelo multi-proyecto").

## Modelo multi-proyecto

El roster de agentes es **un solo equipo compartido** que trabaja para uno o más proyectos. Todo lo específico de un proyecto vive en `projects/<slug>/` (`project.json` + brand-bible/glossary/data-model/icp/product-catalog/roadmap + `agent-overrides/<agente>.md` + `skills/` + `.mcp.json` opcional) más un `.env.<slug>` gitignoreado. El proyecto de ejemplo es **Acme** (`projects/acme`, team de Linear `ACM`).

Core (mejoras una vez → impacta en todos los proyectos): `scripts/agents.ps1` (system prompts con `{{PLACEHOLDERS}}`, incluido `{{OWNER_NAME}}` desde `project.json → ownerName`), `scripts/project.ps1` (`Resolve-ProjectContext` / `Resolve-AgentPrompt` / ruteo por team id), los wrappers, `memory/` y el listener de n8n.

- Los wrappers reciben `-Project <slug>` y `-DryRun` (imprime la config resuelta sin llamar a `claude`).
- El listener de Linear escucha todo el workspace: `respond-linear.ps1` resuelve el proyecto desde `-TeamId` (payload del webhook) o desde el prefijo del identifier del issue (`ACM-12` → acme). Nunca cae en silencio a otro proyecto.
- **Productos multi-repo**: un proyecto puede declarar `productRepos` en `project.json` (sitio de marketing, app, módulos, repos de otro dueño…). `productRepoPath` sigue siendo el repo **primario** (el de Cody). Numa, Greta y Pico reciben TODOS los repos en solo lectura con el placeholder `{{PRODUCT_REPOS}}` (`Get-ProjectRepos` en `scripts/project.ps1`) para seguir el funnel entre repos; Cody puede escribir en los que no son `readOnly` (`{{WRITABLE_REPOS}}`). `scripts/sync-product-repos.ps1` mantiene las copias locales al día y los wrappers lo corren antes de leer código: un análisis sobre una copia atrasada propone sobre código que ya no existe.
- **Fuentes read-only nuevas**: deploys y logs de **Vercel** por un MCP propio con pin de proyectos (`project.json → vercel`, `docs/vercel-readonly-source.md`); bases de producto que no son Supabase por un MCP **MySQL** con guard de SQL (`docs/mysql-readonly-source.md`); gasto de **Google Ads** por el MCP oficial de solo lectura (`docs/google-ads-readonly-source.md`).
- **Regla de oro**: un cambio que mejora cómo trabaja un *agente* → core (`agents.ps1`, wrappers). Un cambio de *dominio* (tablas, tono, stack, comandos de gating) → `projects/<slug>/` (contexto u override). Modelo completo: `projects/README.md`; alta de un proyecto: `docs/add-a-new-project.md`.

## Loop de mejora continua del producto

Un volante semanal por proyecto donde los agentes **generan ideas de mejora proactivamente** y Capi las prioriza en un plan persistente (`projects/<slug>/roadmap.md`). Todo es HITL 1: la persona siempre está entre el plan y la ejecución. Detalle: `docs/product-roadmap-loop.md`.

- **Generadores** (crean `[Proposal]` en Linear): Pico `product-idea-scan`, Cody `tech-debt-scan` (solo lectura, wrapper dedicado `run-cody-scan.ps1`), Numa `funnel-monitor` (anomalía sostenida → propuesta).
- **Dueño del plan**: Capi `pm-progress-review` (wrapper dedicado `run-capi-roadmap.ps1`): reconcilia, re-prioriza, secuencia y **reescribe `roadmap.md`** (su único write, con HARD STOP).
- **Changelog semanal**: Pico `product-shipped-digest` (wrapper dedicado `run-pico-shipped.ps1`, solo lectura + git/gh). Si el proyecto declara `project.json → shippedDigestDiscordWebhookVar` (el NOMBRE de una env var con un webhook de Discord), el wrapper postea además un resumen corto en ese canal.
- **Gate humano**: ningún cron edita código ni abre PRs. El owner aprueba el issue y comenta `Cody:` para construir.

## Project Lead

Por encima del roster hay un **líder de proyecto que NO es un agente del server**: es Claude Code en la máquina del owner, siguiendo la skill de proyecto `.claude/skills/project-lead/` (`SKILL.md` + `references/{triage,plan,follow,alfred}.md`). Existe porque, con varios agentes proponiendo, el cuello de botella deja de ser generar o priorizar ideas y pasa a ser **la decisión del owner**: los `[Plan]` repiten el mismo pedido durante semanas y el Backlog se llena de reportes. Modelo completo y operación: `lead/README.md`.

- **Qué hace**: no recomienda tareas, las lleva. Cada mañana baja Linear, los PRs y **lo que salió en cada app** con `lead/scripts/sync.mjs` (determinístico, sin modelo), empuja y verifica las tareas que ya están en marcha, tría lo nuevo, cierra lo viejo, junta duplicados y propone **hasta tres tareas en marcha a la vez, cruzadas entre proyectos**, con el pedido al agente ya escrito. Con el sí del owner las publica y las sigue hasta producción: reenvía si el agente no respondió, pide la verificación de Qualy, deja el PR leído y listo para mergear y cierra el issue cuando el cambio está en vivo. Además detecta patrones de comportamiento de los agentes y los deja como recomendaciones para Alfred.
- **Verifica contra la app, no contra el issue**: las apps cambian todos los días por fuera de Linear (muchos PRs no nombran un issue) y la base de conocimiento de este repo envejece. Antes de proponer algo, el lead mira `lead shipped` y lee en la rama principal del producto la ruta, la tabla o el proveedor que el pedido nombra. Un pedido a Cody que describe una página que ya es un redirect, o que manda a revisar un proveedor que la app ya reemplazó, es tiempo perdido.
- **Tres vías** (`.claude/skills/project-lead/SKILL.md`): (1) *lo hace y avisa* — lo que solo constata un hecho y se deshace con un clic: archivar reportes leídos, cerrar lo ya hecho con evidencia, juntar duplicados y priorizar el que queda, empujar una tarea aprobada; (2) *propone y, con un sí, lo lleva hasta el final* — tareas nuevas, cerrar algo que no se hizo (`Canceled` es una decisión: los agentes lo leen como «no volver a proponerlo»), recomendaciones para Alfred; (3) *solo el owner* — mergear, plata, credenciales, lo que le habla a un cliente. Qué entra en la vía 1 lo dice `lead/lead.config.json → autonomy`.
- **Lo que un agente tiene se ve en Linear**: el lead pasa el issue a In Progress apenas publica un pedido, y los agentes que producen trabajo (código, verificación, mockup, draft, publicación) también lo mueven al tomarlo (`respond-linear.ps1`); una consulta que se contesta en el comentario no toca el estado, y nunca se reabre un issue cerrado. **A un agente solo lo dispara un comentario** que empieza con `<Agente>:`: un issue nuevo no arranca a nadie. `act.mjs retro` publica ese comentario para los `[Retro]` de Alfred, uno solo para todos, porque Alfred trabaja sobre un único clon.
- **No reemplaza a Capi**: Capi sigue siendo el PM por proyecto y único dueño de `roadmap.md`; su `[Plan]` del lunes es el insumo principal del lead. El lead hace lo que Capi no: el corte diario entre proyectos, el empaquetado de cada decisión y el seguimiento de que se ejecute. Nunca reescribe `roadmap.md`.
- **Piezas** (todo en `lead/`, Node sin dependencias): `scripts/sync.mjs` → `state/snapshot.json`; `scripts/lead.mjs` (CLI del lead, solo estado local: `status` / `brief` / `shipped` / `follow` / `records` / `inbox` / `show` / `triage` / `plan` / `alfred` / `mark` / `task` / `log`); `scripts/act.mjs` (lo único que cambia issues en Linear por script: `close --lane=auto`, `close --ids=… --approved="…"`, `reopen`, `start` para pasar a In Progress lo que un agente ya tiene, `fuse` para fundir varios issues en uno, y `retro` para mandarle a Alfred las recomendaciones aprobadas); `state/tasks.json` (las tareas aprobadas y su etapa, hasta producción); `app/server.mjs` (tablero local opcional en `http://127.0.0.1:4747`; `npm run lead:start` lo deja en segundo plano, `npm run lead:simulacion` trabaja sobre una copia del estado); `lead.config.json` (parte de atención por proyecto, pesos por objetivo, límites, autonomía). Tests: `npm run lead:selftest`.
- **Estado**: `lead/state/` vive en el **checkout principal** aunque la sesión corra en un worktree (se resuelve con `git rev-parse --git-common-dir`); gitignoreado.
- **Dónde corre**: todo en la máquina del owner, nada en la nube (el tablero escucha solo en `127.0.0.1`). La rutina de la mañana es una tarea programada de la app de escritorio de Claude («Hoja del día») y **nunca despierta la máquina**: si estaba suspendida o con la app cerrada, la app lanza una sola corrida de recuperación al volver. Una segunda tarea programada (`seguimiento-del-lead`) revisa cada pocas horas lo que ya se mandó y cierra lo que llegó a producción; se apaga sola cuando no queda nada en marcha. Los prompts de esas tareas están versionados en `lead/scheduled-tasks/hoja-del-dia.md` y `lead/scheduled-tasks/seguimiento-del-lead.md` (con `{{REPO_PATH}}` para la ruta del checkout principal): con ellos se crean las tareas en la app, que las guarda en `~/.claude/scheduled-tasks/`. Si cambias el prompt, cambia el archivo del repo y vuelve a cargarlo en la app.
- **Todo pasa en la charla**: la rutina termina abriendo un chat con lo que hay para mergear (ya leído y verificado), las decisiones rápidas (opciones y recomendación, se contestan con una letra), la limpieza y lo que sigue, **cada issue y cada PR con su link** (salen de `lead brief`). El tablero es opcional. Corre en local porque puede publicar `Cody: …` con la API key del owner: hostearlo pediría un login propio y una lista de emails permitidos chequeada en el servidor.
- **HITL-2, con una franja de bajo riesgo**: `lead.config.json → autonomy` deja en `true` la vía 1 (`archiveRecords`, `closeObviousDuplicates`, `closeVerifiedDone`, `setPriority`, `followThrough`) y en `false` lo que arranca trabajo nuevo (`dispatchCodingAgents`, `dispatchReadOnlyAgents`, `sendAlfredRecommendations`). Sin un sí, el lead no publica un pedido nuevo, no cancela una propuesta, no crea `[Retro]` y nunca mergea. **Ojo**: la app de Claude tiene su propio control de seguridad, aparte de este config, y puede frenar un cierre en lote grande. Cuando frena algo, el lead no lo intenta por otro camino: lo dice en la charla y espera el «ciérralas». Para que lo haga solo, el owner agrega la regla de permiso exacta (`lead/README.md → Permisos`).
- **Clasificación que usa** (`lead/scripts/model.mjs`): un issue es *trabajo* (pide decisión: `[Proposal]`, `[QA…]`, `[Alert]`, hallazgos), *registro* (`[Report]`, `[Plan]`, `[Topics]`, ticks: no se tría; nace abierto porque el owner lo lee en el Backlog, y el lead lo archiva a los 2 días, salvo el `[Plan]` de la semana, que queda hasta que llega el siguiente) o *flujo* (`[Content]` agendado). Si un cron nuevo crea issues, ponle un prefijo `[…]` estable para que caiga en la clase correcta.
- **Credencial y config**: usa `LINEAR_API_KEY` (obligatoria; vía `scripts/op-env.mjs` o, sin op-env, alcanza con la variable en el entorno) y el CLI `gh` con sesión para los PRs y lo que salió en cada app. Opcionales: `LEAD_CONFIG`, `LEAD_STATE_DIR`, `LEAD_PORT`, `LEAD_DRY_RUN`, `LINEAR_TIMEOUT_MS`. De cada `projects/<slug>/project.json` lee `productRepoUrl` o `productRepos[]` (`repoUrl`, `key`, `readOnly`) y `strategicFocus`; en `lead.config.json`, `limits.ownerMinutesPerDay` acota cuánto le pide al owner por día y `alfred.teamKey` dice en qué team van los `[Retro]` (si falta, el del primer proyecto). Si Linear rechaza la key, `sync.mjs` sale con código 2, el tablero queda en solo lectura y el lead arma el plan con el MCP de Linear.

## Tareas comunes

No hay comandos de build ni lint en este repo. Lo que existe:

- **Eval de una skill**: `evals/<skill>/`. Los resultados van a `evals/results/` (gitignoreado).
- **Tests de los MCP propios y del lead**: `cd scripts\mcp-vercel; npm test`, `cd scripts\mcp-mysql; npm test` (sin red ni credenciales) y `npm run lead:selftest`.
- **Correr una skill headless (server Windows)**: `powershell -File scripts\run-skill.ps1 -Skill <skill> [-Project <slug>] [-DryRun]`. El wrapper carga `.env.server` (+ `.env.<slug>` encima vía `scripts/project.ps1`), corre `claude -p` con `--strict-mcp-config` + `--permission-mode dontAsk` + una allowlist mínima de `--allowedTools` (`Read,mcp__supabase__*,mcp__linear__*`) + `--max-budget-usd`, y escribe el `result` del agente en `queue/pending-review/YYYY-MM-DD-<proyecto>-<skill>.md`. Con `-DiscordWebhookVar <VAR>` el destino de la corrida es un canal de Discord: el agente deja el mensaje entre una línea `<discord>` y una línea `</discord>` y el wrapper postea SOLO ese bloque (lo usa el pulso diario de Numa, `funnel-daily-pulse`). Existe un `run-skill.sh` de referencia, pero el runtime vivo es PowerShell en Windows. En el server el repo vive en `C:\agents\agent-team-template` (los workflows de n8n y `docs/server-setup.md` asumen esa ruta; actualízalos si lo mueves). Las flags de la CLI cambian entre versiones: revalida con `claude --help` después de cada upgrade.
- **Workflows de n8n**: viven en `automation/n8n/*.json` y son la fuente versionada. **Impórtalos** en n8n en vez de rearmarlos en la UI; si editas en la UI, re-exporta y sobrescribe el JSON.
- **Nunca recrees ni regeneres desde cero el JSON de un workflow ya publicado.** La copia del repo puede haber driftado respecto de lo que corre en n8n. Antes de cambiar un workflow publicado: (1) pide el JSON exportado actual de n8n, o (2) especifica los cambios exactos (qué nodo, qué campo, qué diff). Aplica el **diff mínimo sobre la versión viva**. Importar una plantilla vieja encima de un listener que funcionaba puede dejar a todos los agentes mudos sin ningún error visible.

Idioma del copy customer-facing: **por proyecto** (`project.json → languageConvention`). Docs internas, memory y prompts de este repo: español neutro con tuteo.

## Convenciones de plugins y skills

- Directorio: `projects/<slug>/skills/<kebab-case>/SKILL.md` para skills del proyecto (el default: `run-skill.ps1` busca ahí primero), o `plugins/<plugin>/skills/<kebab-case>/SKILL.md` para las que sirven a todos los proyectos.
- Frontmatter obligatorio: `name`, `description` (debe arrancar con "Use when ..." — eso dispara el auto-trigger), `hitl_level` (1/2/3), `owner`. Si la corre un agente, agrega `agent:` (lo lee `run-skill.ps1` para resolver tools y modelo). Opcionales que también lee `run-skill.ps1`: `mcp_variant` (una clave de `project.json → mcpVariants` solo para esta skill) y `extra_allowed_tools` (tools separadas por coma que se suman a la allowlist del agente): sirven para una skill que necesita un MCP que su agente no carga normalmente (p. ej. `content-topic-scan` → `seo` + `mcp__gsc__*`) sin tocar el registry. Recomendados: `schedule`, `inputs`, `outputs`, `cost_budget_usd`.
- Naming: `kebab-case`, prefijo por dominio (`ads-*`, `seo-*`, `aeo-*`, `funnel-*`, `content-*`, `signup-*`, `retention-*`), sufijo de acción para generadores (`-optimizer`, `-generator`, `-detector`, `-proposer`, `-monitor`, `-tracker`).
- MCP servers en `.mcp.json` con placeholders `${ENV_VAR}` — nunca secretos inline. El MCP de Supabase corre forzado a `--read-only --project-ref`; el de Linear es el remoto oficial con Bearer `${LINEAR_API_KEY}`. Los demás de solo lectura: GA4 (el oficial `analytics-mcp`), Search Console (propio, `scripts/mcp-gsc/`, solo en `seo.mcp.json`), Core Web Vitals (`scripts/mcp-cwv/`), **Vercel** (propio, `scripts/mcp-vercel/`, en el default y en `qa`), **MySQL** (propio, `scripts/mcp-mysql/`, para bases de producto que no son Supabase) y **Google Ads** (el oficial `google-ads-mcp`, versión fijada, solo para Numa y Greta). Antes de cablear un MCP de terceros, verifica que el paquete exista y haga lo que dice: si no tiene modo de solo lectura, el solo-lectura se impone del lado del repo (guard en el MCP, allowlist en el registry, rol de solo lectura en la cuenta).
- **El agente headless no tiene `Write`** en las skills que corren por `run-skill.ps1`. En Windows las reglas `Write(<glob>)` no matchean la ruta absoluta que usa la tool, y un `Write` pelado dejaría tocar cualquier archivo del repo. Convención: la skill **devuelve el brief como respuesta final** y `run-skill.ps1` lo escribe en `queue/pending-review/`.
  - **Excepción — wrappers dedicados**: una skill con **wrapper propio** puede recibir un `Write` pelado acotado por **HARD STOP** a un archivo puntual, declarado en el `SKILL.md` y en el wrapper (por ejemplo, la memoria de la revisión SEO, las secciones vivas de la estrategia AEO o el `roadmap.md` de Capi). Nunca un `Write(<glob>)`. Un override de proyecto puede autorizar a un agente a appendear en un archivo puntual del repo de agentes, sin commitear.
  - **Excepción mayor — Alfred**: su dominio **es** este repo. Su wrapper (`scripts/run-alfred.ps1`) le da `Edit/Write/Bash` + git/`gh` para editar prompts, wrappers, skills y docs y **abrir PRs**, pero SOLO sobre un **clon limpio** (`ALFRED_REPO_PATH`), nunca sobre la copia viva. Sin clon, degrada a modo PROPOSE (solo lectura, diff como comentario). No toca el repo del producto. Ver `docs/alfred.md`.

## Modelo HITL — no negociable

Toda skill declara `hitl_level:` en el frontmatter:

| Nivel | Comportamiento |
|-------|----------------|
| 1 | Solo lectura. Escribe drafts/alertas. Seguro para correr desatendido. El brief sale como `result` del agente y `run-skill.ps1` lo espeja en `queue/pending-review/`. Si crea issues en Linear, sigue la separación **decisión vs registro** (`memory/CLAUDE.md` → "Linear destination convention"): los dos nacen en `Backlog`, sin asignar, en el team del proyecto, y el tipo decide solo el label — una **decisión** (propuesta, alerta, hallazgo accionable) lleva `agent-proposal` y queda abierta para que el owner la trabaje; un **registro** (reporte, digest, tick de cron) lleva `agent-report`, un título fijo por serie (un issue por corrida, no un hilo de comentarios) y el agente nunca lo cierra: el Project Lead archiva los registros a los 2 días. Una corrida sin novedades **no** crea issue: alcanza con el espejo en `queue/pending-review/`. |
| 2 | Propone una acción y espera el OK humano. El feedback llega desde Linear con un comentario que empieza con `<Agente>:` (por ejemplo `Numa: ¿de qué tabla sale ese número?`) en cualquier team que tenga un `projects/<slug>/project.json`. Los agentes son `Capi/Numa/Greta/Pico/Cody/Qualy/Daly/Leda/Alfred` (roster en `memory/agents-roster.md` + `scripts/agents.ps1`; overrides por proyecto en `projects/<slug>/agent-overrides/`). `automation/n8n/linear-feedback-listener.json` matchea la regex y rutea a `scripts\respond-linear.ps1 -AgentName <nombre> -TeamId <uuid>`, que resuelve el proyecto, carga el prompt resuelto del agente y responde con un comentario que empieza con `🤖 <Nombre> <Emoji>:` (el 🤖 es el guard anti-loop: el agente comenta con la API key de una persona). **Alfred** no corre inline: `respond-linear.ps1` delega en `run-alfred.ps1 -Job issue` para que su loadout no se filtre al listener. No uses `@agente`: el `@` de Linear está reservado para menciones de usuario. |
| 3 | Ejecuta acciones reversibles con audit completo. Hoy hay una sola: `content-topic-scan` de Leda, que carga ideas al banco `topics` del CMS sin aprobación previa (el registro es el issue `[Topics]` + su ledger, y la vuelta atrás es borrar la idea en el admin antes de que el publisher la tome). Dentro de `content-blog-publisher` (nivel 2), el camino `refresh:` se comporta igual: reescribe una nota ya publicada y la publica en la misma corrida si pasa los gates, con issue `[Refresh]` y la versión anterior restaurable desde el historial del CMS. No crees otras de nivel 3 sin auditoría y rollback documentados. |

Si una skill toca producción (base de datos, pagos, email, plataformas de ads): primero dry-run, muestra el diff y espera aprobación. Antes de generar copy customer-facing, la skill carga la brand voice del proyecto (`team-shared/skills/brand-voice` o `projects/<slug>/brand-bible.md`). Antes de citar una métrica, carga el glossary del proyecto para confirmar que la definición coincide con la fuente.

## Tiering de modelos (defaults)

Las skills declaran su modelo con `run-skill.ps1 -Model` (default `claude-sonnet-4-6`, configurado por workflow en `automation/n8n/`). Los agentes del listener declaran su modelo en `scripts/agents.ps1` (campo `Model`, explícito para TODOS, así `ANTHROPIC_MODEL` del env nunca decide en silencio). Los crons que corren por `run-skill.ps1` heredan el modelo del registry: no lo pongas a mano con `-Model` en el workflow salvo que quieras pisarlo a propósito. Política sugerida: nada en Haiku salvo lo realmente trivial; Sonnet por default; Opus para los agentes de alto impacto.

- **Sonnet 4.6** (`claude-sonnet-4-6`) — Capi / Numa / Greta como responders, Qualy, Leda (incluido el tick de publicación). Default de los crons.
- **Opus 5.5** (`claude-opus-5-5`) — Pico (propuestas de producto: razona mejor el trade-off antes de crear el ticket).
- **Opus 4.8** (`claude-opus-4-8`) — Daly (mockups), los crons semanales de SEO/AEO de Greta, el roadmap de Capi y el changelog de Pico (wrappers dedicados, effort high), y **Alfred** (edita prompts y `.ps1` del propio repo: un error de sintaxis en `agents.ps1` rompe a TODOS).
- **Opus 4.7** (`claude-opus-4-7`) con `Effort = 'xhigh'` — Cody. Escribe código en el repo del producto y abre PRs: el loop de mayor riesgo.
- **Haiku 4.5** — solo para ticks triviales que se pasan por `-Model` en n8n (p. ej. `funnel-monitor`). No se asigna a agentes nuevos por default. El tick de Leda NO: con Haiku alucinaba que no podía ejecutar PowerShell y no publicaba. Corre en el Sonnet de Leda y, los días sin posts vencidos, el wrapper sale sin llamar al modelo.

Para subir un agente de versión (misma familia, versión nueva), cambia su `Model` en `scripts/agents.ps1` (es la única fuente: listener y crons lo leen de ahí) y deja el porqué en el comentario de la línea.

**Guard de runaway = TIEMPO, no presupuesto.** Si los agentes corren contra una suscripción (login OAuth), el costo no limita; el riesgo real es un loop colgado. Cada entrada del registry declara `TimeoutMinutes` (`Resolve-AgentTimeout` en `project.ps1`); un watchdog mata el árbol de procesos de claude (incluidos los MCP) al vencer y la corrida se loguea con `timed_out: true`. `--max-budget-usd` queda como respaldo profundo (`PER_RUN_BUDGET_USD` en `.env.server`). Cada corrida agrega una línea de uso (modelo, `cost_usd` nominal, `duration_s`, `timed_out`) a `audit/YYYY-MM-DD.jsonl` vía `Write-AgentAudit`.

Claude Code corre **solo con modelos Claude**. Las keys de Gemini / OpenAI se usan en workflows de n8n o como sub-llamadas dentro de una skill (por ejemplo, generación de imágenes), no como runtime del agente.

## Directorios de runtime (gitignoreados)

- `queue/pending-review/`, `queue/approved/`, `queue/rejected/` — cola compartida entre agentes y personas. `run-skill.ps1` escribe los briefs en `pending-review/` (espejo de lo creado en Linear).
- `queue/sync-backups/` — backups con fecha de los archivos que `sync-agents-repo.ps1` tuvo que descartar para poder hacer fast-forward.
- `queue/.deps-stage/` — staging desechable con los manifests de dependencias de los otros proyectos, para que Qualy cruce una vulnerabilidad compartida sin montar esos repos con permiso de escritura.
- `audit/YYYY-MM-DD.jsonl` — log diario de corridas y decisiones HITL.
- `lead/state/` — snapshot de Linear, triage, plan del día, tareas y registro de decisiones del Project Lead (ver `lead/README.md`).
- `secrets/`, `.env*` — nunca se commitean (salvo los `*.example` y `.env.local.tpl`).

Solo los `.gitkeep` de esos directorios están versionados. Al generar paths de output en skills, usa `queue/pending-review/YYYY-MM-DD-<skill>-<slug>.md`.

## Variables de entorno y secretos

Dos esquemas, a elección (pueden convivir):

- **Archivos planos en el server** (el runtime de los wrappers): `.env.server` (core) + `.env.<slug>` (por proyecto, se carga encima). Plantillas: `.env.example` y `.env.acme.example`. Gitignoreados.
- **1Password + age** (recomendado para la máquina del owner y los agentes interactivos): la fuente de verdad es un item de 1Password; en el repo vive `.env.local.tpl` (referencias `op://` + valores públicos, commiteado) y `.env.local.age` (cifrado por máquina, gitignoreado). Un `.env.local` plano puede no existir. Todo comando que necesite secretos se corre envuelto: `node scripts/op-env.mjs exec -- <cmd>`. Descifra a memoria, sin prompts: apto para agentes desatendidos. `npm run env:push` / `env:pull` / `env:encrypt` / `env:check` / `env:doctor` hablan con 1Password (piden biometría): solo con el owner presente; un agente desatendido no los corre, los pide. Variable nueva: `.env.local` → `env:push` → `env:encrypt`. Guía: `docs/secretos.md`.

Reglas para los dos: nunca imprimir valores de env (ni truncados) y nunca commitear `.env.local`, `.env.local.age`, `.env.server` ni `.env.<slug>`. **Vercel**: el token de la cuenta llega a los agentes como `VERCEL_API_TOKEN` (no `VERCEL_TOKEN`, que el CLI de Vercel tomaría solo del entorno y dejaría a cualquier agente con Bash autenticado para deployar) y solo lo usa `scripts/mcp-vercel/`.

`memory/CLAUDE.md` es el contexto que carga cada agente al inicio de una corrida. Mantenlo corto y denso; el detalle va en `projects/<slug>/` (`brand-bible.md`, `product-catalog.md`, `icp.md`, `data-model.md`…), que los agentes leen bajo demanda. ## Convenciones al editar este repo

- **Archivos `.ps1`**: UTF-8 **con BOM** (PowerShell 5.1 lee sin BOM como CP1252 y rompe emojis y acentos). Después de tocar uno, valida que parsea con el script del repo: `powershell -NoProfile -ExecutionPolicy Bypass -File scripts/check-ps1-parse.ps1 <ruta>` (sale con 0 y `PARSE OK`, o con 1 y los mensajes del parser). No uses un one-liner que gatee por `$?`: `ParseFile` devuelve los errores por su tercer parámetro `[ref]` y no tira excepción, así que `$?` da `$true` aun con un script roto.
- **No toques la identidad anti-loop** (nombre, emoji, firma `🤖 ...`) de ningún agente sin un pedido explícito del owner.
- **Cero secretos, cero PII, cero IDs reales** en archivos versionados. Lo que un tercero deba completar se marca con `TODO(<slug>):` o `{{PLACEHOLDER}}`. Los ids de Vercel (`team_…`, `prj_…`) no son secretos y van en `project.json`; los tokens, nunca.
- Cambios mínimos y quirúrgicos: el registry y los wrappers son compartidos por todos los proyectos.
